**Security and anti-cheat audit — Get Funded!, September 30, 2026.** Three confirmed player-abuse paths were found: two High severity availability issues and one Medium severity memory-exhaustion issue. An encoder/decoder size mismatch increases the persistence risk of the first finding. A separate pricing issue is conditional: its accounting behavior was reproduced, but the required market state was not observed in the normal simulations tested. No game source, configuration, saved place, or published experience was changed.

The strongest protections are working: player ownership comes from the server-supplied Player; numeric remote inputs reject NaN/infinity; trade limits and execution prices are server controlled; duplicate Shop receipts do not debit or grant twice; checkpoint writers are fenced. These protections do not bound the total work or retained state a player can cause.

**F1 — Unlimited free-reset records can degrade or stop the shared exchange.** A normal player needs only to join and Start the free $5K account. No trading, wallet funds, privileged access, or another player is needed. The affected remote is ReplicatedStorage.MarketReign.OrderRequest with Action=Restart and Tier equal to the current instance key, such as F5K:1. Each accepted reset supplies a new instance key for the next request; this is different from replaying a previously reset key.

The entry path is [MarketServer.server.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/MarketServer.server.luau:119>) lines 119–152 and 187–190, through Funded:Restart. [FundedAccounts.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/FundedAccounts.luau:193>) lines 193–197 allow a healthy, untouched free starter to reset. Restart lines 258–293 retire the old attempt and call _open. [FundedAccounts.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/FundedAccounts.luau:172>) lines 172–183 append another account, ledger entry, instance record, and progress/wallet bookkeeping without an account-count ceiling or reset cooldown. The guard at lines 264–265 correctly rejects the same old intent; it does not limit resetting successive fresh accounts.

Retired attempts remain in Engine.AccountOrder and the profile forever. They are scanned by [MarketEngine.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/MarketEngine.luau:312>) lines 312–333 and 509–522, by funded portfolio/statistics/progress functions, and serialized by [WorldCheckpoint.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/WorldCheckpoint.luau:38>) lines 38–56. Full account lists accompany subscribed players' regular updates through [MarketServer.server.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/MarketServer.server.luau:56>) lines 56–69 and [FundedAccounts.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/FundedAccounts.luau:394>) lines 394–435. This raises server CPU, memory, snapshot work, outbound data, and persistence size even if the attacker never places a trade. This game routes everyone to one authoritative exchange, so the blast radius can include players arriving through other servers.

The general 20-token burst / 6-per-second limiter and 256-item execution queue do not bound cumulative retained accounts. The attacker can stay within those limits. All attempts survive checkpoints and disconnects. At the encoded-size limit, [WorldService.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/WorldService.luau:32>) lines 32–41 throws, and Save lines 104–118 marks the entire exchange unhealthy; CanRun lines 95–97 then prevents trading. The actual time to disruptive load depends on the existing exchange and host performance; no production saturation or timing claim is made.

**Related confirmed persistence defect:** Checkpoint.Encode, [WorldCheckpoint.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/WorldCheckpoint.luau:138>) lines 138–143, accepts arbitrary raw JSON sizes. World:_encode checks only the compressed/base64 record against 3,500,000 bytes. Checkpoint.Decode lines 145–152 refuses raw checkpoints above 32,000,000 bytes. Thus a sufficiently large but compressible valid exchange could be successfully saved and later refused on restart. The codec fixture demonstrated 32,000,020 raw bytes encoded into 1,512 bytes, passing the writer's size test and failing the reader. The padding in this fixture is synthetic, not a client-controlled field; it proves the codec mismatch, not an end-to-end player-created oversized save. Cumulative account growth is the identified route toward large real checkpoints. If only the compressed limit is crossed, the current server pauses and may later reload the last valid save; if an overlarge raw checkpoint is committed, normal reopen fails until a safe recovery/migration. Do not confuse those outcomes.

**Evidence and safe reproduction:** Run [isolated-reproductions.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/output/security-audit-2026-09-30/isolated-reproductions.luau>) through an Edit-mode command execution against a disposable copy of this place. It creates new engines/profiles and an injected in-memory store; it does not invoke the live MarketServer, open a real store, or start Play. The reset case performs 200 successive resets using the latest active key. It produced 201 retained attempts, 200 retired accounts, one usable account, and no wallet grant. Raw checkpoint size grew from 135,307 to 296,565 bytes; the portfolio alone reached 96,683 bytes. A checkpoint round trip retained all 201 attempts. A separate fake-world test sets its private MaxEncodedBytes to 1 and confirms Save=false, Healthy=false, and CanRun=false. [codec-boundary.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/output/security-audit-2026-09-30/codec-boundary.luau>) separately demonstrates the raw-size mismatch; it temporarily allocates about 32 MB of input data and accesses no store. Do not repeat these tests against a published server.

**Smallest effective fix:** Immediately enforce a persisted reset cooldown and a conservative retained-attempt ceiling before any retirement or settlement mutation. A cooldown alone only delays exhaustion. Also make the writer enforce the same raw-size limit as the reader before committing. For continuing service beyond the ceiling, compact finalized attempts into bounded lifetime aggregates or move archives out of the hot exchange record, preserving cash/inventory reconciliation, statistics, earned tiers, wallet high-water marks, and replay protection. Global profile growth also needs a storage-capacity plan; a per-user cap does not make one finite shared record scalable indefinitely. Do not simply delete account ledgers, since they participate in accounting and restore validation.

**Fix verification:** Repeated new-key resets must be rejected at the cooldown/ceiling without settling or retiring the current account. Reconnect and restore must not reset the limit. Run enough fixture operations to reach the configured ceiling and show retained state and response sizes plateau. Verify remaining legitimate users can still trade and save. Test raw and encoded sizes on both sides of each limit; every checkpoint the writer accepts must be decodable. Rerun the reconciliation, restart, wallet, statistics, and checkpoint suites.

**F2 — A completed purchase can be replayed to force global save pauses.** The attacker needs one previously successful purchase of an additional funded account using the simulated earned-profit wallet. The cheapest is F5K at $2,000 of game profit. No Robux purchase is involved. Replays need fresh remote Id values, an already used PurchaseSequence, and the same Tier. The outer Seen cache blocks duplicate remote IDs, not a new request carrying a previously committed purchase sequence.

The affected path is OrderRequest Action=Purchase, [MarketServer.server.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/MarketServer.server.luau:176>) lines 176–181 → [WorldService.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/WorldService.luau:124>) World:Purchase lines 124–132 → [FundedAccounts.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/FundedAccounts.luau:297>) Funded:Purchase lines 297–315. Funded:Purchase correctly returns the existing receipt at lines 301–304 without charging again. World:Purchase treats that successful replay like a new purchase: it sets TransactionBusy, assigns PendingPurchase, and defers a complete exchange Save. [WorldService.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/WorldService.luau:95>) CanRun returns false while TransactionBusy is set. Subsequent queued actions also fail the world-availability guard in [MarketServer.server.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/MarketServer.server.luau:154>) lines 154–156.

A player can repeat this after each save completes. Every replay pauses trading for everyone, re-encodes all accounts/market state, and calls UpdateAsync on the shared world key. Real storage latency and throttling can prolong the pause; save errors set Healthy=false until recovery. The server refuses overlapping transactions, but that only serializes the attack. It does not eliminate repeated saves after completion.

**Evidence and safe reproduction:** The purchase case in [isolated-reproductions.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/output/security-audit-2026-09-30/isolated-reproductions.luau>) uses actual WorldService, FundedAccounts, and WorldLease with an injected fake store. A disposable fixture wallet is seeded only to represent an earlier legitimate profit balance. It buys F5K once, then replays sequence 1 ten times. Results: 10 extra store writes, 10 periods with CanRun=false, 11 completion callbacks including the original purchase, exactly two accounts, and exactly one $2,000 debit. This confirms availability abuse while also confirming that item/currency duplication is prevented. No real purchase or DataStore was touched.

**Smallest effective fix:** Distinguish a newly created purchase from a replay. For a receipt known to be durably committed, return the cached/persisted result without TransactionBusy, PendingPurchase, re-encoding, or a new Save. Keep ambiguous/uncommitted purchases pending until durability is established; merely seeing a receipt in memory is not sufficient if an earlier save failed. Add a much lower persistence-operation rate limit for genuinely new purchases to protect the global save path.

**Fix verification:** One purchase must cause one durable debit/grant and one transaction save. Ten or more later replays, including after restore, must cause zero additional saves and zero global pauses while returning the same receipt. Preserve the existing failure-before-commit, lost-commit-response, retry, concurrent-request, and stale-writer behavior. A second player must remain able to trade throughout completed-receipt replays.

**F3 — A client that never subscribes retains replies without a bound.** Any connected player can omit Subscribe and repeatedly submit otherwise valid requests such as Start with fresh IDs. There is no purchase or progression prerequisite.

[MarketServer.server.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/MarketServer.server.luau:35>) add initializes Subscribed=false at lines 35–39. The handler accepts state-changing requests before subscription. [MarketServer.server.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/MarketServer.server.luau:110>) reply unconditionally appends to state.Replies at lines 110–114. Start produces an acknowledgement at lines 168–172 even when it creates nothing. Only a Subscribe request enables periodic output at lines 143–148; the broadcast loop at [MarketServer.server.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/MarketServer.server.luau:285>) lines 285–287 skips unsubscribed clients. Replies are cleared by emit, not by a length or age bound.

The execution queue and Seen history are capped at 256, but Replies is a different collection and has no cap. At the accepted rate of six requests per second, one connected non-subscribing client can retain approximately 21,600 response objects per hour. The actual memory cost depends on payloads and the Lua allocator; a short test did not establish a server crash threshold. Disconnecting releases the client state, and subscribing normally flushes the queue, so this is a sustained session-memory issue rather than durable corruption. Many such sessions amplify it.

**Evidence and safe reproduction:** [server-boundary-harness.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/output/security-audit-2026-09-30/server-boundary-harness.luau>) embeds an unchanged copy of the current MarketServer source and runs it with fake Players, remotes, clock, heartbeat, and disabled background tasks. Pure downstream market modules operate on fresh tables. It spaces 601 Start requests at 0.2 simulated wall-clock seconds each and drains the execution queue after each. It retained 601 replies, sent zero packets, and retained only 256 Seen IDs. A later Subscribe flushed the replies. The extra ownership checks performed afterward explain the final 604-item flush in the result. This is not a load test of actual Roblox transport.

**Smallest effective fix:** Bound Replies by count and age, and either send acknowledgements independently of subscription or discard/coalesce obsolete acknowledgements. A cap such as 64 responses plus a short TTL is a policy choice; ensure clients can recover current state even when old replies are dropped. Apply the same helper to queue-full and rejection responses. Merely reducing the incoming token refill rate does not bound memory.

**Fix verification:** Thousands of accepted non-subscribing requests must leave a bounded reply collection. Successful and rejected actions must obey the same bound. Confirm normal onboarding, purchase completion, subsequent Subscribe synchronization, and disconnect cleanup still work.

**S1 — Conditional pricing issue; not a confirmed reachable player exploit.** [MarketEngine.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/MarketEngine.luau:208>) Engine:_touch lines 208–210 returns the last trade/reference when the requested side of the book is empty. _playerOrder lines 258–274 uses that value for market fills. If the ask is empty while best bid is above last, a player can buy at the lower fallback and immediately sell at the higher bid. The symmetric case is an empty bid with ask below last. Because player fills do not consume book liquidity or advance the tape, the opportunity can be repeated while that quote state persists. Closing profit also credits the wallet through _fillAccount and [FundedAccounts.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/src/FundedAccounts.luau:204>) Reconcile lines 204–214.

A normal participant Submit created such a one-sided book in a disposable engine fixture. Ten five-contract round trips generated $625 of authoritative realized profit and $625 of wallet credit with unchanged bid quantity and zero market volume. The fixture uses server-side setup to create the quote; an attacker cannot submit participant orders through the player remote. This distinction is essential.

I checked three seeds for 8,000 steps each and seed 1729 for 100,000 steps. The longer run included 6,423 one-sided instrument snapshots after the configured 7,200-step warmup, but no crossed fallback quote. Therefore current scheduler/save-state reachability remains unproven. This is conditional Medium severity, with low confidence of current live exploitability, and is excluded from the three confirmed player-abuse findings.

**Safe reproduction and minimal correction:** [pricing-fallback-reproduction.luau](<C:/Users/drews/Development/Roblox Dev/Get Funded!/output/security-audit-2026-09-30/pricing-fallback-reproduction.luau>) creates the fixture and performs the short normal-simulation scans with fresh in-memory engines. It does not send player remotes or access a store. If the fallback is retained, enforce a non-crossing effective spread: a buy fallback must be at least the existing best bid, and a sell fallback at most the existing best ask; adding a one-tick spread is an optional design choice. Alternatively, reject new exposure when that side has no quote while explicitly preserving a safe liquidation policy. Verify long/short one-sided fixtures cannot earn positive P&L from immediate round trips, normal fills remain correct, and closes/depletion cannot get stuck. A definitive exposure test needs representative isolated restored market states or more evidence from the participant generator, not a production exploit.

**Economy, saves, and concurrency.** The implemented Shop is a simulated-wallet shop. No MarketplaceService, ProcessReceipt, PromptProductPurchaseFinished, game-pass ownership handling, donation flow, player-to-player item transfer, or external payment endpoint was found in the active game scripts. There is consequently no basis to claim a missing receipt handler is exploitable here. Creator Hub products/pass catalogs were not inspected; if the experience sells any, their fulfillment code and settings must be supplied for a complete monetization audit. Roblox's official [developer-product guidance](https://create.roblox.com/docs/production/monetization/developer-products) requires ProcessReceipt for actual developer-product fulfillment; the internal PurchaseSequence is not such a receipt.

Trading and wallet data share the world checkpoint, rather than independent per-player saves. WorldLease Claim/Commit uses an owner token and generation, expiry, and nondecreasing saved steps. Followers cannot run a second authoritative market. Purchases stop simulation before saving their debit/account/receipt together, and ambiguous save errors retain the pending transaction. Leaving does not remove positions or reset accounts. These mechanisms and stale-writer/restore/failure behavior were tested with mock stores. Ordinary trades have up to the configured 15-second checkpoint window before durability; catastrophic server failure can roll back unsaved work, but I did not demonstrate a disconnect-only rollback or cross-session duplication exploit.

Per-attempt wallet high-water rewards, permanent earned tiers, and healthy free resets are deliberate in the implementation and existing tests. Automated legal trading may exploit favorable game incentives, but I did not label those policies themselves as a forged-currency or duplicate-reward vulnerability. They should be assessed separately against the intended game economy.

**Defense in depth, separate from confirmed findings.** Use action-specific server budgets for full Subscribe/Stats responses and new persistence transactions; identical subscriptions can be coalesced and account/history output paginated. Retain the existing engine checks. Per-action schemas can also reject irrelevant scalar fields early. Roblox's [client/server security guidance](https://create.roblox.com/docs/scripting/security/client-server-boundary) specifically recommends server rate limits appropriate to expensive operations, not just client-side debounce.

Wrap individual queued action processing in carefully designed error containment so one unexpected handler exception cannot discard the rest of a detached pending batch. This is not evidence of an exploitable exception today; economic mutations should be atomic or failed closed before retries. Instrument capped metrics for remote rejections, retained account count, queued replies, save duration, and raw/compressed checkpoint bytes. Remove unused test modules/diagnostic preview objects from release packaging if convenient, while preserving server-only guards; their present placement was not treated as a privilege escalation.
